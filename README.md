# DevTest Hub

**DevTest Hub** — веб-платформа для автоматизированного развёртывания и управления изолированными тестовыми средами разработчиков на основе Docker.

Проект разработан в рамках курсовой работы по дисциплине «Настройка и администрирование сервисного программного обеспечения».

**Тема курсовой работы:** «Настройка и администрирование инфраструктуры для автоматического развертывания тестовых сред для разработчиков».

## 1. Основные возможности

- Регистрация и авторизация пользователей с помощью JWT.
- Личный кабинет для управления собственными тестовыми средами.
- Создание, просмотр, переименование и удаление сред через REST API.
- Два шаблона развёртывания:
  - **Nginx** — отдельный веб-сервер.
  - **FastAPI + PostgreSQL** — API и база данных в отдельных контейнерах.
- Асинхронная обработка заявок Docker Worker.
- Изоляция сетей и постоянное хранение данных PostgreSQL.
- Автоматическое назначение локальных портов.
- Мониторинг Docker-контейнеров.
- Восстановление некоторых незавершённых развёртываний.
- Защита ресурсов с помощью Docker Labels.
- Подтверждение безвозвратного удаления PostgreSQL Volume.
- Автоматическое обновление статусов в React.
- Модульное и интеграционное тестирование.

## 3. Архитектура

DevTest Hub разделён на независимые компоненты:

```text
                  Пользователь
                       |
                       v
                React Frontend
                  localhost:5173
                       |
                    REST API
                       |
                       v
                FastAPI Backend
                  127.0.0.1:8000
                       |
                       v
              PostgreSQL платформы
                  localhost:5433
                       ^
                       |
                  Docker Worker
                       |
                  Docker Engine
                       |
             +---------+---------+
             |                   |
             v                   v
          Nginx             FastAPI + PostgreSQL
       1 контейнер           2 контейнера
                             отдельная сеть
                             отдельный Volume
```

Backend принимает запросы пользователя и сохраняет задания в основной PostgreSQL.

Worker периодически читает очередь заданий и управляет Docker-ресурсами независимо от Backend и Frontend.

Для автоматических тестов предусмотрена отдельная PostgreSQL на порту `5434`.

## 5. Требования

Для локального запуска необходимы:

- Docker Desktop с работающим Docker Engine.
- Python 3.13 или совместимая версия.
- Node.js и npm.
- Git.
- Установленные Python-зависимости проекта.

Разработка и интеграционные испытания выполнялись на macOS.

Текущая конфигурация рассчитана на локальную доверенную среду разработки, а не на публичный многопользовательский хостинг.

## 6. Подготовка проекта

Клонировать репозиторий:

```bash
git clone git@github.com:LOI1K/DevTest-Hub.git
cd DevTest-Hub
```

Создать локальную конфигурацию:

```bash
cp .env.example .env
```

Указать собственные значения параметров, в том числе:

- `POSTGRES_USER`
- `POSTGRES_PASSWORD`
- `POSTGRES_DB`
- `JWT_SECRET_KEY`

JWT-секрет должен быть криптографически случайным и достаточно длинным.

Файлы `.env` и резервные копии PostgreSQL запрещено публиковать в Git.

Для Python рекомендуется использовать виртуальное окружение `.venv` и установить зависимости Backend и Worker.

## 7. PostgreSQL платформы

Запуск основной и тестовой базы данных:

```bash
docker compose up -d db db_test
```

Проверка состояния:

```bash
docker compose ps db db_test
```

Обе базы должны получить статус `healthy`.

| База                       | Адрес с компьютера |
| -------------------------- | ------------------ |
| Основная `devtesthub`      | `127.0.0.1:5433`   |
| Тестовая `devtesthub_test` | `127.0.0.1:5434`   |

Основная база хранит пользователей, тестовые среды и реестр принадлежащих им Docker-ресурсов.

Тестовая база используется для изолированного выполнения тестов.

### Миграции Alembic

После настройки основной базы выполнить:

```bash
PYTHONPATH=backend python -m alembic upgrade head
```

**Важно:** Alembic использует подключение из `app.database`. Перед запуском необходимо убедиться, что оно направлено именно на нужную базу.

Обычная команда не предназначена для переключения между основной и тестовой БД по одному только параметру `sqlalchemy.url` из `alembic.ini`.

Проверка истории миграций:

```bash
PYTHONPATH=backend python -m alembic history
```

Перед миграцией базы с существующими данными рекомендуется создать резервную копию.

## 8. Запуск Docker Worker

Собрать образ:

```bash
docker compose build worker
```

Запустить:

```bash
docker compose up -d --no-deps worker
```

Проверить:

```bash
docker compose ps worker
docker compose logs --tail=50 worker
```

Worker получает доступ к Docker Engine через `/var/run/docker.sock`.

По умолчанию развёртывание FastAPI + PostgreSQL отключено специальным флагом. Шаблон Nginx при этом остаётся доступным.

  --reload --host 127.0.0.1 --port 8000

Документация REST API:

Интерфейс:

## 11. Шаблон Nginx

Шаблон Nginx создаёт один Docker-контейнер с веб-сервером.

Процесс развёртывания:

1. Пользователь создаёт среду через React.
2. Backend записывает среду со статусом `pending`.
3. Worker получает заявку.
4. Среда переводится в `deploying`.
5. Docker запускает Nginx-контейнер.
6. Назначается локальный TCP-порт.
7. Worker сохраняет Docker ID и порт.
8. Среда получает статус `running`.

Пользователь может открыть веб-сервер по адресу `http://127.0.0.1:<порт>`.

## 12. Шаблон FastAPI + PostgreSQL

Шаблон развёртывает четыре Docker-ресурса:

| Ресурс               | Назначение                 |
| -------------------- | -------------------------- |
| Контейнер FastAPI    | Обработка HTTP-запросов    |
| Контейнер PostgreSQL | Хранение тестовых данных   |
| Docker Network       | Связь между контейнерами   |
| Docker Volume        | Постоянное хранение данных |

Для среды с идентификатором `N` используются имена:

```text
devtest-hub-env-N-api
devtest-hub-env-N-db
devtest-hub-env-N-net
devtest-hub-env-N-data
```

Контейнер API публикует порт только на локальном адресе `127.0.0.1`.

PostgreSQL взаимодействует с API через отдельную Docker-сеть, без публикации её порта на хост.

### Сборка образа API

Из корня проекта:

```bash
docker build \
  -t devtest-hub-fastapi-postgres:dev \
  templates/fastapi-postgres/api
```

Образ должен быть доступен Docker Engine, с которым взаимодействует Worker.

### Маршруты тестового API

| Метод | Маршрут   | Назначение                       |
| ----- | --------- | -------------------------------- |
| GET   | `/health` | Проверка приложения              |
| GET   | `/ready`  | Проверка приложения и PostgreSQL |
| GET   | `/notes`  | Получение тестовых записей       |
| POST  | `/notes`  | Создание записи                  |
| GET   | `/docs`   | Swagger UI                       |

Корневой маршрут `/` в тестовом API не реализован и может возвращать `404 Not Found`. Для документации нужно открывать `/docs`.

## 13. Включение FastAPI + PostgreSQL

Для использования шаблона необходимо включить его одновременно в Backend, Worker и Frontend.

### Worker

Дополнительный Compose-файл:

`compose.fastapi-test.yaml`

```yaml
services:
  worker:
    environment:
      DEVTEST_HUB_ENABLE_FASTAPI_POSTGRES: "1"
```

Запуск Worker с поддержкой нового шаблона:

```bash
docker compose \
  -f compose.yaml \
  -f compose.fastapi-test.yaml \
  up -d --no-deps --build worker
```

### Backend

```bash
DEVTEST_HUB_ENABLE_FASTAPI_POSTGRES=1 \
PYTHONPATH=backend \
python -m uvicorn app.main:app \
  --reload --host 127.0.0.1 --port 8000
```

При выключенном флаге Backend отклоняет попытку создания FastAPI + PostgreSQL-среды с HTTP `503`.

### Frontend

```bash
cd frontend
VITE_ENABLE_FASTAPI_POSTGRES=true npm run dev
```

Этот флаг открывает выбор нового шаблона в интерфейсе.

**Важно:** флаг Frontend не является механизмом авторизации или защиты сервера. Решение о доступности шаблона также проверяет Backend.

Файл Compose с включённой функцией предназначен для локального тестирования и демонстрации.

## 14. Реестр Docker-ресурсов

Для многоконтейнерных сред используется таблица:

`environment_resources`

Она содержит:

- Идентификатор среды.
- Тип ресурса: контейнер, сеть или том.
- Роль ресурса.
- Ожидаемое имя Docker-ресурса.
- Docker ID, если применимо.
- Время регистрации.

Реестр позволяет проверять принадлежность ресурсов и контролировать удаление.

Для ресурсов также используются служебные Docker Labels.

Worker не должен автоматически удалять неизвестные ресурсы или объекты, принадлежность которых не подтверждена.

## 15. Статусы сред

| Статус      | Значение         |
| ----------- | ---------------- |
| `pending`   | Ожидает создания |
| `deploying` | Развёртывается   |
| `running`   | Работает         |
| `stopped`   | Остановлена      |
| `failed`    | Ошибка           |
| `deleting`  | Удаляется        |

Некоторые статусы предусмотрены моделью данных, но не все пользовательские операции для них реализованы.

Frontend периодически получает актуальные состояния через REST API без необходимости обновлять страницу вручную.

## 16. Безопасное удаление

Удаление выполняется асинхронно.

Backend возвращает HTTP `202 Accepted` и переводит среду в `deleting`.

### Nginx

Для удаления Nginx достаточно подтвердить действие в интерфейсе.

Worker проверяет принадлежность контейнера, удаляет его и соответствующую запись PostgreSQL.

### FastAPI + PostgreSQL

Удаление этого шаблона уничтожает:

1. Контейнер FastAPI.
2. Контейнер PostgreSQL.
3. Изолированную сеть.
4. Docker Volume со всеми данными.

В интерфейсе пользователь видит предупреждение и должен ввести точное название среды.

Backend требует явного параметра:

```http
DELETE /api/v1/environments/{id}?delete_volume=true
```

Подтверждение сохраняется в PostgreSQL в поле `delete_volume_on_delete`.

Worker повторно проверяет это разрешение перед фактическим удалением.

Без подтверждения удаление FastAPI + PostgreSQL отклоняется.

**Удаление Docker Volume необратимо без заранее созданной резервной копии.**

## 17. Восстановление после сбоев

При запуске Worker проверяет незавершённые задания.

### Nginx

Для Nginx реализовано восстановление по Docker-контейнеру и проверенным метаданным.

В зависимости от состояния контейнера среда может быть восстановлена или переведена в `failed`.

### FastAPI + PostgreSQL

Восстановление многоконтейнерной среды выполняется только после проверки необходимых ресурсов.

Проверяются контейнеры, сеть, том, служебные метки, параметры подключения и состояние сервисов.

Если инфраструктура неполная или некорректная, автоматическое восстановление пропускается для последующей диагностики.

Непроверенные Docker-ресурсы не удаляются автоматически.

### Защита от параллельных Worker

Основной Daemon использует PostgreSQL Advisory Lock.

Это защищает очередь от одновременной обработки несколькими экземплярами Daemon, использующими одинаковую блокировку.

### Ограничения

Восстановление не гарантирует исправления всех возможных сбоев Docker Engine и PostgreSQL.

Для производственной эксплуатации необходимы дополнительные механизмы обработки ошибок, ограничения времени выполнения операций и централизованные журналы.

## 18. Мониторинг

Worker выполняет два вида периодической работы:

- Приблизительно раз в 5 секунд — обработка заявок.
- Приблизительно раз в 60 секунд — проверка работающих сред.

### Мониторинг Nginx

Проверяются наличие контейнера, Docker ID, служебные метки, состояние и сетевой порт.

Для подтверждённо неисправных контейнеров возможно изменение статуса среды на `failed`.

### Мониторинг FastAPI + PostgreSQL

Проверяются два контейнера, сеть, том, принадлежность ресурсов, healthcheck и доступность API.

Монитор различает состояния `healthy`, `port_changed`, `degraded` и `unknown`.

При подтверждённом изменении локального порта он может безопасно синхронизировать его с PostgreSQL.

Временная неготовность PostgreSQL после перезапуска может отображаться как `degraded`, а затем возвращаться в `healthy`.

Мониторинг нового шаблона не выполняет автоматическое удаление или перезапуск неисправных ресурсов.

## 20. Интеграционные испытания

Проверен полный жизненный цикл FastAPI + PostgreSQL-среды:

1. Создание через React.
2. Регистрация задания в PostgreSQL.
3. Создание двух Docker-контейнеров.
4. Создание изолированной сети и тома.

10. Перезапуск контейнера PostgreSQL.

12. Подтверждение удаления через интерфейс.

## 21. Диагностика

Состояние сервисов:

```bash
docker compose ps
```

Логи Worker:

```bash
docker compose logs --tail=80 worker
```

Docker-контейнеры:

```bash
docker ps -a
```

Docker-сети:

```bash
docker network ls
```

Docker-тома:

```bash
docker volume ls
```

Список сред можно посмотреть через авторизованный REST API или SQL-запрос к основной PostgreSQL.

При использовании дополнительных файлов Compose необходимо указывать ту же конфигурацию, с которой запускались соответствующие сервисы.

### Рассинхронизация состояний

Состояние контейнера Docker и статус в PostgreSQL могут временно или постоянно различаться после некоторых сбоев.

Перед ручным исправлением необходимо проверить Docker ID, имя контейнера, служебные метки, порт и фактическую доступность приложения.

Нельзя исправлять статус произвольным SQL-запросом без проверки принадлежности и текущего состояния ресурсов.

## 22. Остановка сервисов

Остановить Worker:

```bash
docker compose stop worker
```

Остановить сервисы Compose:

```bash
docker compose stop
```

Для просмотра логов:

```bash
docker compose logs -f worker
```

Выход из просмотра логов выполняется через `Ctrl + C` и не останавливает контейнер.

**Не используйте `docker compose down -v`, если необходимо сохранить данные PostgreSQL.**

Контейнеры тестовых сред создаются Worker отдельно от сервисов Compose и управляются через DevTest Hub.

## 23. Безопасность и ограничения

Текущая конфигурация предназначена для доверенной локальной эксплуатации.

Docker Socket предоставляет Worker высокие привилегии над Docker Engine.

Важные ограничения:

- Отсутствие полноценной многопользовательской изоляции Docker Engine.
- Отсутствие строгих ресурсных квот для всех тестовых контейнеров.
- Локальное хранение некоторых конфигурационных параметров.
- Ограниченные возможности восстановления после частичных сбоев.
- Отсутствие производственного механизма резервного копирования данных каждой тестовой среды.

Для публичного развёртывания необходимы дополнительные ограничения доступа, управление секретами, аудит операций, ресурсные лимиты и усиленная изоляция.

## 25. Итог

DevTest Hub демонстрирует автоматизированное управление жизненным циклом тестовых сред разработчиков.

В проекте объединены веб-интерфейс, REST API, PostgreSQL, асинхронная обработка заданий, Docker, мониторинг, восстановление и безопасное удаление ресурсов.

Разработанная система предназначена для учебной демонстрации практических навыков настройки и администрирования сервисного программного обеспечения.
