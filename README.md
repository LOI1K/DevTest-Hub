# DevTest Hub

DevTest Hub — веб-платформа для автоматического развёртывания и управления тестовыми средами разработчиков.

Проект разработан в рамках курсовой работы по дисциплине «Настройка и администрирование сервисного программного обеспечения».

**Тема:** «Настройка и администрирование инфраструктуры для автоматического развертывания тестовых сред для разработчиков».

## 1. Возможности

- Регистрация и авторизация пользователей с использованием JWT.
- Личный кабинет с управлением тестовыми средами.
- Создание тестовых сред на основе Docker-контейнеров.
- Автоматическое развёртывание nginx.
- Отображение статуса, идентификатора и адреса среды.
- Автоматическое обновление статусов без перезагрузки страницы.
- Асинхронное удаление тестовых сред.
- Хранение информации о пользователях и средах в PostgreSQL.
- Фоновая обработка заявок отдельным Docker Worker.
- Запуск инфраструктурных сервисов через Docker Compose.
- Автоматические тесты Backend и Frontend.

## 3. Архитектура

Платформа состоит из четырёх основных компонентов.

### Frontend

React-приложение предоставляет пользовательский интерфейс для регистрации, авторизации и управления тестовыми средами.

Frontend взаимодействует с Backend через REST API.

### Backend

FastAPI обрабатывает HTTP-запросы, проверяет авторизацию и управляет данными пользователей и тестовых сред.

При создании среды Backend записывает заявку в PostgreSQL со статусом `pending`.

При запросе удаления Backend переводит среду в статус `deleting`.

### PostgreSQL

База данных хранит сведения о пользователях, тестовых средах, их статусах, идентификаторах Docker-контейнеров и назначенных портах.

Для тестирования предусмотрена отдельная база данных.

### Docker Worker

Worker работает как отдельный сервис Docker Compose.

Каждые пять секунд он проверяет PostgreSQL на наличие заявок.

При обнаружении заявки на создание Worker запускает Docker-контейнер и обновляет статус среды.

При обнаружении заявки на удаление Worker удаляет принадлежащий среде контейнер и соответствующую запись PostgreSQL.

Worker выполняется независимо от Frontend и Backend.

## 6. Настройка окружения

Клонировать репозиторий:

```bash
git clone git@github.com:LOI1K/DevTest-Hub.git
cd DevTest-Hub
```

Создать локальный `.env` на основе `.env.example`:

```bash
cp .env.example .env
```

Указать собственные значения переменных:

- `POSTGRES_USER` — пользователь PostgreSQL.
- `POSTGRES_PASSWORD` — пароль PostgreSQL.
- `POSTGRES_DB` — основная база данных.
- `JWT_SECRET_KEY` — секретный ключ JWT длиной не менее 32 символов.

Для локального запуска Backend используются настройки подключения `127.0.0.1:5433`.

Внутри Docker Compose Worker подключается к PostgreSQL по имени сервиса `db` и порту `5432`.

Файл `.env` не должен публиковаться в GitHub.

Перед использованием приложения необходимо применить миграции Alembic к соответствующей базе данных.

## 7. Запуск PostgreSQL

Запустить основную и тестовую базы данных:

```bash
docker compose up -d db db_test
```

Проверить состояние:

```bash
docker compose ps
```

Ожидается состояние `healthy` для обоих сервисов.

Подключения с локального компьютера:

| База                | Адрес          |
| ------------------- | -------------- |
| Основная PostgreSQL | 127.0.0.1:5433 |
| Тестовая PostgreSQL | 127.0.0.1:5434 |

## 8. Запуск Docker Worker

Собрать Docker-образ:

```bash
docker compose build worker
```

Запустить Worker в фоновом режиме:

```bash
docker compose up -d worker
```

Проверить его состояние:

```bash
docker compose ps worker
```

Посмотреть последние сообщения:

```bash
docker compose logs --tail=30 worker
```

Следить за логами в реальном времени:

```bash
docker compose logs -f worker
```

Выход из просмотра логов выполняется через `Ctrl + C`. При этом сам контейнер продолжает работать.

Worker автоматически запускается повторно согласно политике `restart: unless-stopped`.

## 9. Запуск Backend

В корне проекта активировать предварительно настроенное Python-окружение:

```bash
source .venv/bin/activate
```

Запустить FastAPI:

```bash
PYTHONPATH=backend python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Backend будет доступен по адресу:

http://127.0.0.1:8000

Интерактивная документация REST API:

http://127.0.0.1:8000/docs

## 10. Запуск Frontend

В отдельном терминале выполнить:

```bash
cd frontend
npm install
npm run dev
```

Frontend будет доступен по адресу:

http://localhost:5173

Для локальной разработки Vite перенаправляет запросы `/api` на Backend, работающий по адресу `127.0.0.1:8000`.

## 11. Создание тестовой среды

1. Открыть DevTest Hub в браузере.
2. Зарегистрироваться или войти в существующий аккаунт.
3. Перейти в личный кабинет.
4. Ввести название новой среды.
5. Создать среду с шаблоном `nginx`.
6. Дождаться автоматического развёртывания.

Последовательность обработки:

```text
React
  |
  v
FastAPI
  |
  v
PostgreSQL: pending
  |
  v
Docker Worker
  |
  v
Docker Engine
  |
  v
nginx-контейнер
  |
  v
PostgreSQL: running
  |
  v
React: отображение готовой среды
```

После запуска пользователь получает адрес среды с автоматически назначенным локальным портом.

Страница личного кабинета периодически запрашивает актуальные данные через REST API, поэтому статус изменяется без ручной перезагрузки.

## 12. Удаление тестовой среды

Пользователь выбирает нужную среду в личном кабинете и нажимает кнопку удаления.

Backend переводит запись в состояние `deleting`.

Docker Worker обнаруживает заявку, проверяет принадлежность контейнера проекту и выполняет удаление.

После удаления контейнера соответствующая запись удаляется из PostgreSQL.

Карточка среды автоматически исчезает из личного кабинета.

## 13. Статусы тестовых сред

| Статус      | Значение                  |
| ----------- | ------------------------- |
| `pending`   | Ожидает обработки         |
| `deploying` | Выполняется развёртывание |
| `running`   | Среда запущена            |
| `stopped`   | Среда остановлена         |
| `failed`    | Ошибка развёртывания      |
| `deleting`  | Ожидает удаления          |

Наличие статуса не означает, что для него уже реализована отдельная пользовательская операция. Например, полноценное управление остановкой и повторным запуском сред может быть добавлено в дальнейшем.

```bash
docker compose ps
```

Просмотр логов Worker:

```bash
docker compose logs --tail=50 worker
```

Просмотр работающих Docker-контейнеров:

```bash
docker ps
```

Проверка списка тестовых сред в PostgreSQL:

```bash
docker compose exec -T db psql -U devtest -d devtesthub -c "SELECT id, name, status, host_port FROM environments ORDER BY id;"
```

В последней команде `devtest` и `devtesthub` соответствуют локальной конфигурации разработки. При использовании других значений `.env` их необходимо заменить.

## 16. Остановка сервисов

Остановить только Worker:

```bash
docker compose stop worker
```

Остановить сервисы Docker Compose:

```bash
docker compose stop
```

Команда остановки сервисов не удаляет тома PostgreSQL.

**Внимание:** не используйте `docker compose down -v`, если необходимо сохранить данные баз. Ключ `-v` удаляет тома, управляемые Compose.

Контейнеры тестовых сред создаются Worker отдельно от сервисов Compose, поэтому их жизненным циклом необходимо управлять через приложение или предусмотренные инструменты Worker.

## 20. Восстановление после сбоев

В DevTest Hub реализован механизм восстановления незавершённых развёртываний.

### Восстановление при запуске Worker

При запуске Docker Worker проверяет PostgreSQL на наличие тестовых сред со статусом `deploying`.

Поддерживаются следующие сценарии:

1. Если Docker-контейнер отсутствует, среда переводится в статус `failed`.
2. Если контейнер существует, работает и прошёл проверку принадлежности проекту, восстанавливаются статус `running`, Docker ID и порт.
3. Если контейнер не прошёл проверку принадлежности или его состояние некорректно, автоматическое восстановление пропускается.

Восстановление запускается автоматически при старте Docker Worker.

### Ручная диагностика

Проверка незавершённых развёртываний без изменения данных:

```bash
docker compose run --rm --no-deps worker python -m worker.recover_once
```

Режим применения изменений:

```bash
docker compose run --rm --no-deps worker python -m worker.recover_once --apply
```

Режим `--apply` следует использовать только при отсутствии параллельно выполняемых операций развёртывания.

### Защита от одновременных Worker

Docker Worker использует PostgreSQL Advisory Lock.

Это предотвращает одновременную обработку очереди несколькими экземплярами обновлённого Daemon, использующими одинаковую блокировку.

### Корректная остановка

Worker обрабатывает сигнал `SIGTERM`, завершает цикл обработки и освобождает PostgreSQL Advisory Lock.

Для завершения операций в Docker Compose настроен `stop_grace_period: 30s`.

### Очистка осиротевших контейнеров

При удалении среды без сохранённого Docker ID Worker проверяет наличие контейнера по ожидаемому имени.

Перед удалением проверяются служебные метки принадлежности DevTest Hub.

Если проверка не пройдена, контейнер не удаляется.

### Ограничения

Текущий Recovery выполняется при запуске Worker, а не непрерывно во время его работы.

Механизм не восстанавливает автоматически все возможные ошибки Docker Engine, повреждения PostgreSQL или потерю связи с базой данных.

Для промышленной эксплуатации необходимы дополнительные механизмы мониторинга, повторных попыток и контроля активных операций.
